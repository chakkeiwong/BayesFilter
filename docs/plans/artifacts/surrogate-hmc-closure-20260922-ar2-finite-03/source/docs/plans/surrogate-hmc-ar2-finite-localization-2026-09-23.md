# AR2 finite-target failure localization — 2026-09-23

This is the next bounded action in the existing surrogate-HMC closure master.
It follows finite-preflight-02, which found seven typed numerical failures in
the outer prior probes. The question is whether those failures are sensitive
to arithmetic precision or persist in the correction algorithm when the same
realized particle and reset design is evaluated in FP64.

The target remains the unchanged AR2 finite DCTR likelihood and its canonical
Contract-E correction. The FP64 arm is an independent diagnostic of arithmetic
sensitivity; it is not an admitted claim route because the scoped controls and
claim run are FP32/TF32. No control, particle design, likelihood value,
support rule, force substitute, or integration domain is changed.

## Evidence contract

- Question: what mechanism explains the seven finite-endpoint failures?
- Comparator: the exact same ten probe rows, rounded particle/noise/reset
  design, observations, controls, and canonical call chain in FP32 and FP64.
- Primary diagnostic classification: FP32_PRECISION_SENSITIVITY when every
  failed FP32 probe is valid in FP64; BOTH_PRECISIONS_CORRECTION_FAILURE when
  any failed probe remains invalid in FP64; otherwise MIXED_PRECISION_RESULT.
- Vetoes: changed design or controls, missing raw failure status, non-finite
  observability tensors, row/batch wiring failure, or source drift.
- Explanatory diagnostics: failure code/stage/time/particle, filtering and
  post-reset covariance minimum eigenvalues, filtering ESS, and coordinate-cap
  observables. These diagnose the failure; they do not promote a finite
  posterior.
- Nonclaims: no finite-posterior existence, quadrature accuracy, D/R or C/D
  agreement, HMC validity, default readiness, or support truncation follows.
- Artifact: versioned surrogate-hmc-closure-20260922-ar2-finite-03 with
  source snapshot, prior-report/tensor hashes, FP32/FP64 status tensors, and
  machine-readable per-probe rows.

The seven failed rows come from finite-02's frozen preflight report. Three
healthy rows are replayed in the same batch path to expose a replay or wiring
failure. The FP64 target uses the same rounded design generated by the target
constructor; equality of each input tensor and every non-design control is
checked before interpretation.

## Assumption and resource audit

The previous result is the provenance for the failed-row set. FP32/TF32 is
the claim execution scope; FP64 is a diagnostic precision-transfer
hypothesis. A precision rescue would show arithmetic sensitivity but would not
make the FP64 route claim-bearing. Persistence in both arms would implicate
correction conditioning or the realized cloud and triggers inspection of the
recorded margins before any numerical repair.

The finite pass cap remains 6,000 CPU-worker seconds and 7,500 GPU-wall
seconds. This localization attempt reserves at most 1,000 CPU-worker and
1,500 GPU-wall seconds, with the existing focused review. It is bounded to
one fresh versioned attempt and does not reopen either completed B/R or A/R.
A failed attempt is repaired only for harness/infrastructure issues within
this same budget. No dense quadrature is launched from this stage.

## Skeptical audit and pre-mortem

The audit passes: the target, baseline, and diagnostic classification are
explicit; invalid numerical values remain failures; FP64 is not silently
promoted; and the stage cannot certify a posterior. The main misleading
outcome is a precision rescue caused by a changed particle design, which is
why input tensors and controls are compared exactly. Another is a failure in
both arms caused by the same cloud but with insufficient observability; the
saved covariance, ESS, cap, and first-failure fields allow that explanation
to be checked. If the stage completes, the next master action is chosen from
the classification and remains bounded by the finite-pass budget.
