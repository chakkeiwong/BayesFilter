- Question: whether the prematurely stopped seed A and B states remain trainable through a substantial fixed continuation budget.
- Exact baseline: the verified `best_trainer_state` embedded in the historical seed A `checkpoint-1500.json` and seed B `checkpoint-2500.json`. Seed B's file is a container whose controller labels step 2500, but its embedded state is optimizer step 2250; the embedded state is the actual baseline.
- Primary campaign pass criterion: each seed completes 4,000 additional optimizer updates and emits all required finite checkpoints, selection, audit, support, manifest, and result artifacts without a continuation veto.
- Veto diagnostics: the continuation vetoes in the intent ledger apply immediately. Monitoring loss is not a veto and cannot stop training.
- Explanatory-only diagnostics: all continuous loss, gradient, scale, acceptance-independent, runtime, and allocator measurements are descriptive.
- Nonclaims: a pass nominates a checkpoint for separately retuned sequential fixed-HMC evaluation; it establishes no convergence or posterior claim.

## Frozen execution protocol

Each seed runs in a separate process. `CUDA_VISIBLE_DEVICES=1` exposes only physical GPU 1, which appears to TensorFlow as logical `/GPU:0`. GPU 0 is not visible to either parent. Both parents must set `TF_FORCE_GPU_ALLOW_GROWTH=true`, call the repository memory-growth helper before device initialization, and verify GPU placement of trainer variables and representative transport outputs.

Target values and analytic scores are generated by 25 persistent CPU/XLA workers per seed, one core per worker and four rows per worker. Each optimizer update therefore consumes a batch-native 100-row target batch. Seed A workers use CPUs 0--24 and seed B workers use CPUs 25--49. CPU workers explicitly hide all GPUs. Transport forward/log-determinant, reverse-KL differentiation, Adam, and parameter state run on GPU in FP64 with XLA JIT enabled. No scalar target fallback, `tf.map_fn`, `tf.vectorized_map`, or row-mapped training route is allowed.

For each seed:

1. Validate the exact source checkpoint SHA-256 and joint-checkpoint payload.
2. Construct the original trainer config and restore `best_trainer_state`, including Adam moments and iteration.
3. Set the continuation LR without resetting Adam.
4. Save continuation checkpoint 0, then run 4,000 additional updates.
5. Use LR `2e-4` for continuation updates 1--2,000, `1e-4` for 2,001--3,000, and `5e-5` for 3,001--4,000.
6. At continuation updates 500, 1,000, ..., 4,000, save state and evaluate one fixed 500-row monitoring bank. Monitoring is telemetry only and cannot change LR, restore state, select a checkpoint, or stop training.
7. After update 4,000, evaluate checkpoint 0 and all eight continuation checkpoints on a fixed, disjoint 500-row selection bank. Select the lowest finite mean reverse-KL loss; ties use the earlier continuation step.
8. Evaluate the selected checkpoint exactly once on an untouched 500-row audit bank, then run the finite support, coordinate-shell, and round-trip checks.

The monitor, selection, and audit banks use new 2026-08-06 stateless seeds and are mutually disjoint by construction. Training streams also use new continuation seed folds. The selection bank is checkpoint-selection data, not evidence of HMC or posterior validity. The audit is an untouched descriptive/veto diagnostic, not a training controller.

## Skeptical plan audit

- Wrong baseline: corrected. The baseline is the embedded best trainer state, not the terminal state or controller label. Seed B's step-label mismatch is recorded rather than hidden.
- Proxy promotion: corrected. Monitor, selection loss, and audit loss can nominate a saved transport only; none can establish NeuTra convergence or HMC validity.
- Missing stop conditions: corrected. Only explicit numerical, target, device, resource, artifact, and wall-budget vetoes stop training.
- Unfair comparison: this is not a method-ranking experiment. Both seeds receive the same continuation budget, LR schedule, batch topology, and evaluation sizes.
- Hidden defaults: architecture, optimizer state, target, backend, batch topology, LR schedule, cadence, seeds, sizes, and cap are classified above.
- Stale context: current policy requires serious NeuTra training on GPU, so the historical CPU campaign is used only as a warm-start and timing source.
- Environment mismatch: GPU visibility, memory growth, physical/logical mapping, CPU affinity, worker GPU hiding, TensorFlow/XLA, and source hashes are required manifest fields.
- Artifact adequacy: full checkpoints, fixed-bank losses, device/resource telemetry, run manifests, result files, and supervisor summary answer the bounded continuation question.

## Pre-mortem

The run could pass while misleading us if selection loss improves but HMC geometry remains poor. The separate HMC retuning gate prevents that inference. It could fail because two TensorFlow parents contend for GPU resources rather than because NeuTra is invalid; the two-update concurrent canary and allocator telemetry discriminate this. It could fail because a CPU worker is not truly pinned or batch-native; PID, affinity, shard, and policy checks fail closed. It could look flat because the LR schedule is poor; that is a tuning repair trigger, not evidence against the model or NeuTra family.
