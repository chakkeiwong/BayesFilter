seeds. The finite-program value error relative to the float64 dense diagnostic

## Tuning And Engineering

Calibration seeds were `3401,3402`, validation seeds were `3411,3412`, and the
claim seeds above were untouched. The selected controls were:

```text
epsilon = 2.0
sinkhorn_steps = 8
ridge = 1e-5
```

The selected arm's validation mean error was `-0.146812` and its representative
recursive-versus-central-FD maximum discrepancy was `0.011468`. Differences
among neighboring tuning arms were tiny and based on only two validation
seeds. Thus this arm is a frozen representative setting, not a statistically
supported globally optimal setting.

All claim rows were finite and placed on GPU. Maximum row and column residuals
were `1.97e-7` and `2.04e-5`, both below `1e-2`. The process used TensorFlow
2.19.1, float32 tensors, TF32, XLA, verified memory growth, and an RTX 4080
SUPER. Total process wall time was `26.706` seconds, including tuning, XLA
compilation, and claim execution.

The isolated feasibility process observed a conservative TensorFlow allocator
peak of `75,340,288` bytes. Claim rows, measured after tuning in a process with
retained allocator state, reported `16,311,552` bytes peak. These are
context-dependent allocator measurements, not hard memory caps.

## Post-Run Red Team

The strongest alternative explanation is favorable cancellation on this single
fixed observation sequence. A second untouched observation data set or a
same-data paired ladder whose CI excludes the observed accuracy would overturn
the current scope conclusion. The weakest evidence is the two-seed tuning
selection, not the 16-seed value interval. A candidate failure here would have
rejected this scope only; the successful result does not establish general
nonlinear accuracy.
