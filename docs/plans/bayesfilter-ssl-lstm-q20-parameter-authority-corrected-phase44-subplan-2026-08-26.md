## Question

Does increasing the independently generated post-training theta bank from
`N=256` to `N=512` reduce the bank-A support/outlier behavior under exactly the
same frozen NeuTra trainer state, or does support variability remain?

This is a support and finite-particle diagnostic. It is not an objective,
architecture, whitening, posterior, HMC, or canonical LEDH experiment.

## Frozen boundary and changed scope

The target is unchanged: the batch-native q=20 SSL-LSTM target has
`theta in R^4`; the 60D UKF state is internal. The old v2.2 root-group
training rows (232 rows), normalized weights, proposal family, beta schedule,
M0/C0 semantics, four NeuTra arms, 200 optimizer updates, target signature,
and GPU/XLA policy are frozen. Banks A, B, and C remain untouched contextual
audits and are never used for training, tuning, or selection.

The only claim-bank change is a fresh N=512 M0 bank generated by the existing
Phase 28 pilot runner with seed `(20260826, 4404)`. The calibration-only cloud
is 128 rows rather than the N=256 pilot's 64. This is a particle-count-scaled
campaign hypothesis, not a promoted default and not part of the optimizer
measure. The claim bank itself contains 512 rows. The pilot's protocol hash
must still equal the frozen M0/C0 hashes because particle count is recorded as
configuration, while target/proposal/schedule semantics are unchanged; the
runner separately checks `particles == 512` and `calibration == 128`.

Each arm reconstructs one trainer and evaluates A, B, C, and N=512 only after
the final update. The terminal state hash must equal the v2.4 reference hash.
This makes the comparison a bank-size/support audit rather than a retraining
comparison.

## Evidence contract

**Hard gates before interpretation:**

1. The N=512 pilot is `PASS_THETA_MEASURE_PILOT`, finite, target-signature
   exact, measure `theta_R4`, and has the frozen M0/C0 protocol hashes.
2. Its M0/C0 particle and calibration counts are exactly 512 and 128, and all
   authority/A/B/C/N512 pilot receipts and required tensor hashes are distinct.
3. The old root-group split is complete, row-disjoint, and root-disjoint.
4. One batch-native GPU/XLA trainer per arm consumes only the old training rows;
   all four banks are evaluated only after the last update.
5. Every terminal state hash equals the matching v2.4 reference hash.
6. All target/status, score, transport-parity, and support tensors are finite.

Residual or support differences are explanatory diagnostics, never a
promotion criterion. A passing phase only establishes that this finite audit
was executed faithfully.
